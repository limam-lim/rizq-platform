# باقة الرد الصوتي الذكي (Rizq Voice Agent)
## دليل معماري للتنفيذ المستقبلي — Documentation Only, No Live Code

> **ملاحظة أساسية:** هذا الملف تخطيطي بحت. لا يوجد أي API key أو حساب فعلي مربوط بالمنصة حالياً لأي من الخدمات المذكورة (Twilio, Vapi.ai, Bland.ai, Make.com, n8n). حسب قرارك السابق، أي تكامل يتطلب اشتراكات مدفوعة متكررة مؤجَّل حتى تسجيل الشركة وشراء الاستضافة — لكنه أولوية فور توفر أوراق الشركة، لأن Twilio/WhatsApp Business هما جوهر الجاذبية التجارية للمنصة. هذا المستند جاهز لتُبنى عليه لاحقاً دون إعادة تصميم.
>
> **ملاحظة تحديث:** تم حذف تكامل الآفاتار المرئي (HeyGen) من هذا المستند بناءً على قرارك — غير ضروري ولا علاقة له بالمكالمة الصوتية.

---

## 1. لماذا هذه الباقة تصلح لرزق تحديداً

الباقة تخدم فئة الحسابات التجارية (متجر/مكتب/معرض) التي تدفع أكثر (Diamond وما فوق) وتحتاج تغطية اتصال 24/7 بدون تكلفة توظيف موظف استقبال. هي طبقة إضافية فوق نظام الأدوار الحالي (`isDiamondActive`, `rizq_call_handler.js`) وليست نظاماً موازياً — أي تنفيذ مستقبلي يجب أن يمر عبر نفس بوابة التحقق من الباقة الموجودة حالياً في `server.js` / `rizq_package_lifecycle_agent.js`.

## 2. المكوّنات والأدوار

| الطبقة | الخيار المقترح | الدور |
|---|---|---|
| الاتصال الهاتفي (Telephony) | Twilio (رقم افتراضي أو Porting لرقم موريتاني عبر SIP trunk) | استقبال/تحويل المكالمات الواردة |
| تنسيق المحادثة الصوتية (Voice Orchestration) | Vapi.ai أو Bland.ai | يربط Twilio بمحرك STT → LLM → TTS دون بناء pipeline يدوي |
| الفهم والرد (LLM) | Claude API (نفس المزوّد المستخدم في `rizq_manager_agent`) | يقرأ سياق التاجر (خدمات، أسعار، أوقات عمل) ويكوّن الرد |
| التحويل الصوتي | مدمج داخل Vapi/Bland (deepgram/elevenlabs عادة) | STT عربي دارجة + TTS طبيعي |
| الأتمتة بعد المكالمة | Make.com أو n8n | تثبيت الحجز، إرسال تأكيد واتساب/بريد، تحديث لوحة التاجر |

**قرار معماري مهم:** لا تُبنى منطق المحادثة (الأسعار، الخدمات، سياسة الرد) داخل Vapi/Bland مباشرة. تبقى "مصدر الحقيقة" (source of truth) في قاعدة بيانات رزق (`server.js` + ملفات الحساب)، وتُستدعى عبر webhook في كل مكالمة. هذا يمنع ازدواجية البيانات بين لوحة التاجر والمساعد الصوتي — نفس المبدأ المطبَّق حالياً بين `rizq_manager_agent` والموقع.

## 3. تدفق العمل (من استلام المكالمة إلى تأكيد الحجز)

```
[زبون يتصل بالرقم]
        │
        ▼
   Twilio (يستقبل الاتصال)
        │  webhook
        ▼
   Vapi.ai / Bland.ai (ينشئ جلسة صوتية)
        │  GET /api/voice-agent/context?accountId=XXXX   ← جديد، من رزق
        ▼
   خادم رزق يرجّع: اسم التاجر، الخدمات/المنتجات، الأسعار،
   أوقات العمل، سياسة الحجز، لغة العميل (AR/FR)
        │
        ▼
   محرك المحادثة (STT → Claude LLM → TTS)
        │  أثناء المكالمة: قد يحتاج تأكيد حجز/موعد
        ▼
   إذا طلب العميل حجزاً → Vapi/Bland يستدعي:
   POST /api/voice-agent/booking-intent   ← جديد، من رزق
        │
        ▼
   خادم رزق يسجّل الطلب في نفس نموذج `rizq_bookings`/`rizq_sub_requests`
   (يُستخدم نموذج بيانات موحّد لا نموذج منفصل خاص بالصوت)
        │
        ▼
   Make.com / n8n (webhook من رزق بعد الحفظ)
        │
        ├──► إرسال تأكيد واتساب للزبون
        ├──► إرسال تأكيد بريد/واتساب للتاجر
        └──► تحديث لوحة التاجر (نفس الـ dashboard الحالي، تبويب جديد "المكالمات والحجوزات")
        │
        ▼
   نهاية المكالمة → Vapi/Bland يرسل ملخص + تسجيل (اختياري) إلى:
   POST /api/voice-agent/call-log   ← جديد، من رزق (للتحليلات + مراجعة الجودة)
```

## 4. نقاط تكامل خادم رزق المطلوبة (مستقبلاً، غير مبنية بعد)

هذه Endpoints ثلاثة فقط، تُضاف إلى `server.js` بنفس نمط الحماية الحالي (`BACKEND_SHARED_SECRET` + التحقق من الباقة):

1. **`GET /api/voice-agent/context?accountId=`**
   يرجّع JSON بمحتوى المتجر/المكتب (خدمات، أسعار، أوقات عمل، رقم تواصل بديل، اللغة الافتراضية). يُبنى من نفس مصادر البيانات المستخدمة حالياً في صفحات `rizq_store.html` / `rizq_office.html` العامة — لا حاجة لنموذج بيانات جديد، فقط aggregation endpoint.

2. **`POST /api/voice-agent/booking-intent`**
   Body: `{accountId, customerPhone, service, requestedTime, notes}`. يُخزَّن في نفس نموذج الحجوزات المستقبلي (إن لم يوجد بعد، يُبنى كجدول جديد بسيط `rizq_bookings.json` بنفس نمط JSON-store الحالي في المشروع، وليس قاعدة بيانات منفصلة).

3. **`POST /api/voice-agent/call-log`**
   لتخزين ملخص المكالمة + رابط التسجيل (إن وُجد) لأغراض جودة الرد ومراجعة التاجر لاحقاً من لوحته.

**التحقق من الصلاحية:** كل استدعاء من Vapi/Bland يجب أن يمر أولاً على تحقق `isDiamondActive(accountId)` (أو الباقة المخصصة لهذه الميزة تحديداً — يُقترح "باقة الرد الصوتي" كباقة إضافية منفصلة قابلة للشراء فوق Diamond، وليس ميزة مجانية ضمن Diamond، لأنها تحمل تكلفة تشغيلية شهرية فعلية بعكس بقية الميزات).

## 5. حقول لوحة التاجر المطلوبة (Dashboard UI مستقبلي)

قسم جديد "المساعد الصوتي" داخل `rizq_dashboard_store.html` / `_office.html` / `_corp.html`، يحتوي:

- تفعيل/إيقاف الميزة (تتطلب اشتراك الباقة أولاً)
- اختيار رقم هاتف مخصص (من الأرقام المتاحة عبر Twilio) أو استخدام رقم رزق المشترك
- حقول "قاعدة معرفة المساعد": أسئلة شائعة يجيب عنها المساعد، نبرة الرد (رسمي/ودّي)، رسالة ترحيب مخصّصة
- سجل المكالمات (تاريخ، مدة، نتيجة: حجز/استفسار/تحويل لبشري)
- زر "تحويل لبشري" — رقم الطوارئ الذي يُحوَّل إليه إذا فشل المساعد أو طلب الزبون ذلك صراحة

## 6. الأمان والخصوصية

- تسجيلات المكالمات (إن فُعِّلت) تحتاج موافقة صريحة معلنة للزبون في بداية المكالمة (متطلب قانوني/أخلاقي بغض النظر عن التشريع المحلي).
- بيانات رقم هاتف الزبون تُخزَّن فقط لغرض الحجز، بنفس سياسة الخصوصية المطبقة على بيانات الطلبات الحالية في المنصة.
- الاتصال بين Vapi/Bland وخادم رزق يجب أن يستخدم نفس `BACKEND_SHARED_SECRET` الحالي أو مفتاح مخصص منفصل — لا يُفتح endpoint بدون توقيع.

## 7. التسعير التقديري (تخطيطي فقط، للمرجعية عند التفاوض لاحقاً)

| الخدمة | نموذج التسعير الشائع |
|---|---|
| Twilio | رقم شهري (~$1-2) + دقائق مكالمة (~$0.01-0.02/دقيقة) |
| Vapi.ai / Bland.ai | اشتراك شهري + سعر لكل دقيقة صوت (يتفاوت، عادة $0.05-0.15/دقيقة) |
| Make.com / n8n | n8n ذاتي الاستضافة (self-hosted) مجاني إن استضيف على نفس سيرفر رزق مستقبلاً، أو Make.com بخطة شهرية |

**التوصية:** عند التنفيذ الفعلي، تبدأ الباقة كـ "إضافة مدفوعة اختيارية" فوق Diamond وليس ميزة ضمن أي باقة حالية، لأن تكلفتها التشغيلية مرتبطة مباشرة باستخدام كل تاجر (على عكس بقية الميزات ذات التكلفة الثابتة).

---

**الخلاصة:** البنية جاهزة للتنفيذ متى تم فتح الحسابات المدفوعة. لا تعارض مع أي كود مبني حالياً — كل نقطة تكامل مقترحة تُبنى فوق النماذج والبوابات الموجودة (الباقات، الحسابات، Rizq ADS) دون تكرارها.
